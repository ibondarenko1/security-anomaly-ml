# Security Anomaly ML v0.1 Product Plan

## Goal

Turn the current research-grade detector into a consumable open-source product that a third party can run on their own CICFlowMeter-compatible network-flow data without retraining the model or understanding the research pipeline.

The v0.1 success criterion is:

> A new user can install or run one container, submit CICFlowMeter-compatible flows, and receive versioned analyst-facing security incidents with no access to training labels or research datasets.

## Frozen detection pipeline

The first product release preserves the already-evaluated logic:

```text
CICFlowMeter-compatible flows
        -> schema validation
        -> causal temporal-context features
        -> frozen Context Random Forest
        -> attack score
        -> flow threshold 0.10
        -> Policy B incident aggregation
           key = src_ip + dst_ip + dst_port
           window = 5 minutes
        -> promotion if max_attack_score >= 0.25
        -> analyst-facing incidents
```

v0.1 must not silently retrain, retune, whitelist, suppress, or change thresholds.

## Separation of product and research code

Research paths may continue to use labels, fixed UNSW capture dates, evaluation manifests, and experiment-specific artifacts.

The product inference path MUST NOT require:

- `Label` / `attack_cat`;
- Jan 22 / Feb 17 / Feb 18 dates;
- UNSW ground truth;
- retraining before use;
- evaluation-only scripts.

## Input contract v1

Initial support is intentionally narrow: CICFlowMeter-compatible CSV/records only.

### Required identity/context fields

- `Flow ID` (optional for scoring but accepted/preserved when present)
- `Src IP`
- `Src Port`
- `Dst IP`
- `Dst Port`
- `Protocol`
- `Timestamp`

### Required model fields

The exact 76 frozen CICFlowMeter baseline feature names used by the Context model MUST be exported into a versioned machine-readable feature contract, e.g. `contracts/feature-contract-v2-128.json`.

The validator must reject missing required model fields before scoring and report all missing/invalid columns in one error response.

### Input rules

- timestamps must be parseable and sortable;
- source/destination ports must be integers in `[0, 65535]`;
- protocol must be representable by the frozen model contract;
- model numeric features must be finite or handled exactly as defined by the frozen preprocessing contract;
- out-of-order batch input may be sorted internally, but output must retain a stable source-row identifier;
- same-timestamp flows must use the existing tie-safe causal semantics: no flow at timestamp `t` can use another flow at the same timestamp as history.

## Temporal state contract

The inference engine must reproduce the frozen 43 temporal context features exactly.

State is derived from prior flows for source/destination entities over the existing 10-second, 60-second, and prior-history windows.

Two supported modes are planned:

1. `batch`: state starts empty at the beginning of the submitted file/run.
2. `stream`: state persists for the lifetime of the running service and is updated only after each complete same-timestamp peer group is scored.

v0.1 may ship batch mode first. Streaming support must use the same feature semantics.

## Model artifact contract

The pretrained release artifact must include:

- frozen Context Random Forest binary;
- model SHA256;
- model version;
- feature-contract version;
- preprocessing/feature-builder version;
- Python version;
- scikit-learn version used for serialization;
- flow threshold `0.10`;
- aggregation policy `B / 5m`;
- promotion threshold `0.25`;
- training/evaluation provenance summary;
- license/redistribution statement for the artifact.

Recommended identifiers:

```text
product_version: 0.1.0
model_version: context-rf-v2
feature_contract: cicflow-v2-128
incident_contract: incident-v1
```

The runtime must refuse to load an incompatible model/feature-contract combination.

## CLI contract

Primary v0.1 user interface:

```bash
security-anomaly analyze flows.csv --output incidents.jsonl
```

Expected optional commands:

```bash
security-anomaly validate flows.csv
security-anomaly version
security-anomaly model-info
```

The CLI should return non-zero exit codes for schema/model/runtime failures and concise actionable errors.

## Incident output contract v1

Default output: JSON Lines, one promoted incident per line.

Minimum fields:

```json
{
  "schema_version": "incident-v1",
  "incident_id": "stable-id",
  "first_seen": "2026-08-17T12:00:00Z",
  "last_seen": "2026-08-17T12:03:21Z",
  "src_ip": "10.0.0.12",
  "dst_ip": "10.0.0.8",
  "dst_port": 445,
  "protocol": 6,
  "flow_count": 18,
  "max_attack_score": 0.73,
  "mean_attack_score": 0.31,
  "promoted": true,
  "model_version": "context-rf-v2",
  "feature_contract": "cicflow-v2-128"
}
```

Optional but useful fields may include source-row IDs, representative flow metadata, score statistics, and evidence counters. Do not invent attack-family labels unless a separate validated classifier supplies them.

## API contract

API is secondary to the CLI and should reuse the exact same inference core.

Minimum endpoints:

```text
GET  /health
GET  /version
GET  /model
POST /v1/analyze/batch
GET  /metrics
```

No duplicate model logic inside FastAPI handlers.

## Packaging

v0.1 should support two paths:

### Python package

```bash
pip install .
security-anomaly --help
```

### Docker

```bash
docker run --rm \
  -v "$PWD:/data" \
  security-anomaly-ml:0.1.0 \
  analyze /data/flows.csv --output /data/incidents.jsonl
```

The container must include the compatible pretrained model or obtain it through a deterministic verified release-artifact step.

## End-to-end reproducibility test

Maintain a small redistributable synthetic fixture containing benign-like and anomalous-like CICFlowMeter-compatible flows.

A release smoke test must execute the real path:

```text
fixture CSV
 -> validation
 -> temporal features
 -> frozen model
 -> threshold
 -> aggregation
 -> promotion
 -> incident JSONL
```

Expected incident IDs/counts/scores should be snapshot-tested within appropriate numeric tolerance.

## CI release gate

Every PR/release should run:

1. unit tests;
2. input-contract tests;
3. causal temporal-feature regression tests;
4. model/feature-contract compatibility test;
5. end-to-end fixture test;
6. CLI smoke test;
7. Docker build and container smoke test.

A release is blocked if the frozen inference fixture changes unexpectedly.

## Observability

Minimum runtime metrics:

- flows processed;
- rejected flows;
- processing rate;
- attack-score summary/distribution;
- flow alerts;
- aggregated incidents;
- promoted incidents;
- processing latency;
- loaded product/model/contract versions.

Prometheus-compatible metrics are sufficient for v0.1.

## Security and privacy

Before v0.1 release add:

- `SECURITY.md` with vulnerability-reporting instructions;
- statement that network-flow metadata may contain sensitive IP/host information;
- no outbound telemetry by default;
- documented local data retention behavior;
- dependency scanning in CI;
- model artifact SHA256 verification before load.

## Explicitly out of scope for v0.1

Do not block the first usable release on:

- packet capture / raw PCAP ingestion;
- live NIC sniffing;
- Kafka;
- Kubernetes;
- multi-user SaaS;
- web dashboard;
- automated retraining;
- attack-family classification;
- whitelisting/suppression tuning;
- GPU support;
- another ML architecture search.

## Definition of Done for v0.1.0

A clean machine can:

1. clone the repository or pull the container;
2. obtain/verify the pretrained model automatically or from the GitHub Release;
3. run the provided synthetic example successfully;
4. analyze a valid CICFlowMeter-compatible user file without labels;
5. receive `incident-v1` JSONL output;
6. identify the exact model/product/feature-contract versions used;
7. run the complete test suite and container smoke test;
8. read clear limitations and privacy/security documentation.

Only after these conditions are satisfied should the repository describe itself as a usable v0.1 product. It should still not claim production readiness until it is validated on independent real networks and the remaining operational alert burden is addressed.
